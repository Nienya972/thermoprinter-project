1. Общие сведения

Версия v1 — рабочий прототип системы удалённой печати, где пользователь отправляет текст Telegram-боту, а мини-компьютер (Linux) принимает запросы и печатает на термопринтере через USB.

Цель v1 — получить стабильную базовую реализацию (альфа) и показать архитектуру: очередь печати, логирование, ограничение нагрузки и контроль доступа.

2. Назначение системы

  • Приём текстовых сообщений от пользователя через Telegram.
  • Проверка запроса (правила использования, бан-лист, лимиты, фильтрация текста).
  • Запись информации о запросе в журнал (SQLite).
  • Последовательная печать текста на термопринтере (ESC/POS).

3. Состав системы

3.1 Аппаратная часть

  • Мини-компьютер (например, Raspberry Pi / другой Linux-совместимый SBC).
  • Термопринтер 80 мм (USB, ESC/POS).
  • Термобумага 80 мм.

3.2 Программная часть

  • Telegram-бот (режим long polling).
  • Core-модуль (управление логикой обработки).
  • Security Layer: согласие с правилами, бан-лист, лимиты (tokens/cooldown), фильтрация текста.
  • Очередь заданий (print queue) и worker печати (print worker).
  • Логирование (SQLite): пользователи, задания, статусы, причины отказов.
  • Драйвер печати ESC/POS.

5. Алгоритм работы

  1. Пользователь отправляет текст Telegram-боту.
  2. Проверка согласия с правилами использования.
  3. Проверка бан-листа пользователя.
  4. Проверка лимитов (tokens/cooldown).
  5. Фильтрация текста по стоп-словам и шаблонам.
  6. Создание задания печати и запись в журнал.
  7. Постановка задания в очередь.
  8. Worker печатает задания последовательно.
  9. Система обновляет статус и отправляет ответ пользователю.

6. Ограничения v1

  • Только текст. Печать изображений не входит в v1 (будет добавлено в v2).
  • Ограничение длины сообщения и частоты запросов.
  • Очередь ограничена по размеру, чтобы не допустить бесконечного накопления задач.

7. Устойчивость и безопасность

7.1 Ограничение нагрузки (tokens)

Для предотвращения злоупотреблений применяется квотирование по модели token bucket: у каждого пользователя есть баланс токенов, одна печать списывает токены, а затем они восстанавливаются со временем (дополнительно может применяться cooldown).

7.2 Очередь печати

Печать выполняется последовательно: все запросы превращаются в задания и обрабатываются worker-ом по одному, что исключает конфликт доступа к принтеру.

7.3 Логирование

В SQLite сохраняются: идентификатор пользователя, время запроса, статус выполнения, причина отказа. Это повышает прозрачность и помогает при отладке.

7.4 Автовосстановление

Сервис может быть оформлен как демон (systemd) с автоперезапуском при сбое, чтобы исключить ручной контроль.

8. Тестирование (план для v1)

  • Burst: серия запросов от одного пользователя → часть отклоняется по лимитам.
  • Multi-user: несколько пользователей → задания печатаются последовательно через очередь.
  • Fault: ошибки принтера (нет бумаги/отключение) → корректное сообщение пользователю и запись в лог.

9. Перспективы развития

  • Печать изображений: resize → grayscale → dithering → 1-bit bitmap → ESC/POS.
  • Удалённое управление несколькими устройствами (ID принтера, централизованные логи).
  • Расширенные меры контроля при публичном использовании.
